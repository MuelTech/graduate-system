# RAP-C1 — Freeze + immutable snapshot + required signatures + conclusion readiness

**Branch:** `refactor/collaborative-defense-workspace`
**Scope:** the pre-conclusion RAP lifecycle inside the collaborative Defense
Workspace. This completes the WF-C1c requirement absorbed into the CDW initiative.
**Canonical authority:** `docs/superpowers/COLLABORATIVE_DEFENSE_WORKSPACE_AND_RAP_SOURCE_OF_TRUTH.md` (§9–§11) and `docs/superpowers/DEFENSE_WORKFLOW_SOURCE_OF_TRUTH.md` (§14–§15).

## System-only authoring

The official Committee Report / RAP MUST be authored **inside the system** from the
existing structured canonical `RapReport.bodyDocument` (the CDW-5 Word-like editor).
**No Word/DOCX/PDF upload path was added** — there is no `sourceType = UPLOADED_FILE`,
no document import, and no external-report fallback. The canonical lifecycle is:

```
Rapporteur authors in-system → Save Draft → Freeze report
  → immutable canonical snapshot/version/hash
  → required signers sign the exact frozen artifact
  → RAP FINALIZED → Chairman records the verdict → CONCLUDED
```

## Freeze (Rapporteur)

`POST /thesis/defense/:scheduleId/collaboration/report/freeze`
(`DefenseCollaborationService.freezeReportForSignatures`).

- **Authorization:** only the exact assigned `RAPPORTEUR` `PanelAssignment` for the
  exact schedule (Chairman/Panelist/Adviser/Facilitator/wrong-Rapporteur → 403).
- **Preconditions:** report exists, status `DRAFT`, not already frozen; session in a
  writable status (not `CONCLUDED`/`CANCELLED`); body is valid + has meaningful
  content; all required numeric evaluators (Chairman + Panelists) are FINALIZED and
  the Oral Examination Summary exists or is safely generated by the existing
  transaction-safe helper. No score, rating, or verdict is derived.
- **Transactional:** runs inside the shared per-attempt lock (`SELECT … FOR UPDATE`
  on the schedule row) used by collaboration writes, with a `bodyVersion` CAS. It
  atomically canonicalizes the body, increments `contentVersion`, computes the
  deterministic server SHA-256 of the COMPLETE signing snapshot (fixed metadata +
  canonical body; verdict-independent), persists `frozenAt`/`frozenById`/
  `frozenContent`/`frozenContentHash`, sets status `FOR_SIGNATURE`, and creates the
  required signer roster.
- **Idempotent/race-safe:** a second freeze returns the existing frozen snapshot
  (`alreadyFrozen: true`) and never replaces it; `createMany(..., skipDuplicates)`
  prevents duplicate signer slots.

## Required signer policy (stage-aware, exact attempt)

Derived at freeze time from the exact attempt's `PanelAssignment` roster
(`rap-signature.policy.ts`):

| Stage | Required signers |
|---|---|
| TITLE_DEFENSE | Chairman + assigned Panelists + Rapporteur (**no Adviser**) |
| PROPOSAL_DEFENSE | active **Adviser** + Chairman + Panelists + Rapporteur |
| FINAL_DEFENSE | active **Adviser** + Chairman + Panelists + Rapporteur |

**Facilitator is never a signer. Dean is never a signer** (Dean approval remains a
separate, unconfirmed institutional requirement). No slot is fabricated.

## Signing

`POST /thesis/defense/:scheduleId/collaboration/report/sign`
(`signReportForSignatures`).

A required signer signs ONLY their own slot, for the exact frozen version/hash,
inside the same per-attempt lock:

- the RAP must be frozen and open for signatures (`FOR_SIGNATURE`/`PARTIALLY_SIGNED`);
- the caller must have a `required` slot on that exact RAP (unrelated users,
  Facilitator, and non-signers → 403);
- an already-signed slot → 409 (deterministic, no duplicate signatures);
- evidence must be image e-signature data (`data:image/…`), reusing the existing
  project convention — no new raw-signature model;
- the write records `signedAt`, `signedContentHash` = frozen hash, and
  `signedContentVersion` = frozen `contentVersion`.

The final required signature drives a monotonic, race-safe aggregate recompute
(`RapReportService.recomputeRapStatus`) that moves the RAP to `FINALIZED` and sets
`finalizedAt` once. Status progression: `DRAFT → FOR_SIGNATURE → PARTIALLY_SIGNED →
FINALIZED` (the existing `RapStatus` enum is reused; no new values).

## Conclusion readiness (Chairman)

The official RAP must be authored in-system, and the formal verdict requires that
in-system Committee Report to be **FINALIZED** first — at **every** stage
(Title / Proposal / Final). The repository conclusion transaction is the final
authority and enforces this BEFORE any authoritative write (DefenseConclusion,
ThesisRecord, session CONCLUDED):

```
NO RAP            → 409
DRAFT             → 409
FOR_SIGNATURE     → 409
PARTIALLY_SIGNED  → 409
ALL_SIGNED        → 409 (the canonical lifecycle auto-transitions to FINALIZED)
DISTRIBUTED       → 409
FINALIZED         → eligible, subject to the remaining prerequisites
```

There is **no legacy bypass**: a missing in-system `RapReport`, or any
non-`FINALIZED` status, blocks a NEW conclusion; legacy Rapporteur notes never
substitute for the RAP, and the conclusion path never creates or mutates a RAP.
`validateConclusionPreconditions` treats a `null`/`undefined` `rapReportStatus` as
fail-closed. Only PASSED / REDEFENSE_REQUIRED are accepted; scores never select the
verdict; the frozen report/hash/version/signatures are never mutated by the
conclusion.

Already-CONCLUDED historical attempts (including legacy ones with no in-system RAP)
remain readable and unchanged — this rule only gates recording a NEW conclusion.

`GET /thesis/defense/:scheduleId/collaboration/conclusion-readiness` returns the
authoritative facts the Chairman UI renders (evaluations, Summary, report frozen,
signatures x of y, RAP finalized, blockers) and agrees with the transaction and the
service validation.

## Collaboration lock after freeze

Once frozen, the committee report body and the attempt collaboration layer become
read-only: new annotations/comments/replies are rejected server-side
(`assertCollaborationWritable` for RAP statuses `FOR_SIGNATURE`/`PARTIALLY_SIGNED`/
`ALL_SIGNED`/`DISTRIBUTED`/`FINALIZED`) and the client (`isCollaborationActive`)
disables the composer. Historical comments remain fully readable.

## Frontend

- **Rapporteur:** `rap-signature-panel.tsx` — a Committee Report readiness checklist
  and a non-casual two-step **Freeze for Signatures** confirmation that states what
  freezing locks.
- **Frozen (all roles):** version + `N of M` signature progress + the required
  signer roster (name, role, Pending/Signed, timestamp). A required unsigned signer
  gets a **Sign / E-Sign** action (reusing `ESignaturePad`). Raw signature
  images/blobs are never rendered — only status.
- **Chairman:** `chairman-verdict-panel.tsx` — explicit readiness (evaluations,
  Summary, report frozen, signatures x of y, RAP finalized) and, only when ready, a
  PASSED / Re-defense Required selector with confirmation. Surfaced from the role rail.
- **Report body:** once frozen, `canEditBody` is false and the workspace renders the
  report read-only.

## Integrity guarantees

- The frozen `RapReport.bodyDocument` is immutable for the frozen version.
- Every signature binds the exact frozen version + hash.
- `signedContentHash` mismatch / stale version is impossible via the freeze gate
  (signing reads the frozen hash under the lock); a non-frozen or non-signable RAP
  is rejected.
- Conclusion is atomic and never rewrites frozen content; `REDEFENSE_REQUIRED`
  keeps the concluded attempt immutable (a later re-defense is a new attempt).

## Migration

**NO NEW DATABASE MIGRATION.** CDW-1 already introduced the required persistence
(`RapReport.contentVersion/frozenAt/frozenById/frozenContent/frozenContentHash`,
`RapReportSignature.roleAtDefense/required/isSigned/signedAt/signedContentHash/
signedContentVersion`, `@@unique([rapId, userId])`). No schema change was needed.
